# Diseño de ingeniería — Connector Hub y SaaS Billing\n\n**Proyecto:** Construction Automation / REAL-PROOF\n**Fecha:** 2026-10-22\n**Estado:** Diseño técnico listo para implementación por fases; no habilita proveedores ni cobros reales.\n**Regla de liberación:** todas las integraciones externas y facturación de suscripción siguen en modo cerrado hasta superar compilación, pruebas de integración, revisión de seguridad y una aceptación explícita de producción.\n\n## 1. Decisión ejecutiva\n\nConstruir un **monolito modular** con un Connector Hub interno y un subsistema separado de SaaS Billing. Mantener PostgreSQL, Spring Boot y el outbox existentes; no desplegar microservicios nuevos hasta que escala, aislamiento operacional o requisitos de disponibilidad lo justifiquen.\n\nOrden recomendado:\n\n1. Corregir las fronteras de confianza y crear contratos de conectores.\n2. Completar la entrada durable de webhooks y la entrega asíncrona de eventos salientes.\n3. Migrar Procore a un adapter OAuth real y verificable, primero en sandbox.\n4. Añadir suscripciones SaaS en Stripe Test Mode, separadas de pagos de facturas de obra.\n5. Medir, reconciliar y probar recuperación antes de abrir producción.\n\n**No ejecutar aún** el generador de “Parte 6” presentado en la conversación. El repositorio ya contiene `V15__construction_niche_ops.sql`, `V16__identity_templates_integration.sql` y tablas de plantilla, integración y outbox. Reutilizar el número V15 chocaría con el historial Flyway; además, ese generador no es seguro ni compatible sin cambios sustanciales (sección 12).\n\n## 2. Evidencia del sistema actual\n\nInspección del árbol empaquetado, no inferencias del README:\n\n- `src/main/resources/db/migration/V16__identity_templates_integration.sql`: crea `integration_outbox`, `external_id_map`, `document_template` y tablas con RLS.\n- `src/main/java/com/tuempresa/integration/procore/ProcoreController.java`: endpoint `/webhooks` devuelve 501 deliberadamente hasta implementar autenticación, deduplicación y procesamiento inbound.\n- `ProcoreClient.java`: usa un bearer token estático por configuración; si no hay credenciales opera en DRY-RUN. El cliente no declara límites explícitos de conexión/lectura ni OAuth lifecycle.\n- `ProcoreBridgeService.java`: `pushRfiNow()` llama a Procore en línea y luego escribe un evento `PUSHED` al outbox. Mezcla ejecución externa y persistencia dentro de una operación transaccional.\n- `IntegrationOutboxService.java`: inserta mensajes en `integration_outbox`, pero no se encontró un worker dedicado que reclame, entregue, reprograme y coloque esas filas en dead letter.\n- `platform/events/OutboxPoller.java`: procesa `projection_outbox`, no `integration_outbox`. Son colas diferentes; el worker actual no demuestra entrega externa.\n- `V4__billing.sql`: el dominio de factura/pago es **finanzas de construcción** (`invoice`, `payment_application`, `payment`), no facturación SaaS.\n- `PaymentApplicationService.java`: solicitud de pago de subcontratista con validación de factura, contrato y compliance. No debe compartir tablas ni transiciones con las suscripciones comerciales de Megalodón/Construction Automation.\n- `V15`, `V16`, `V17`, `V18`, `V19`, `V20` y `V21` ya existen. Toda evolución debe ser una migración **aditiva V22+**, sin editar migraciones históricas.\n\n## 3. Arquitectura objetivo\n\n```text\n                               ┌─────────────────────────────┐\nProcore / ERP / custom webhook ─► Ingress por proveedor       │\nStripe Billing webhook ─────────► verificación / normalización│\n                               └──────────────┬──────────────┘\n                                              │ transacción corta\n                                     ┌────────▼────────┐\n                                     │ connector_inbox │  dedup + estado durable\n                                     └────────┬────────┘\n                                              │ worker\n                                   ACL / Adapter / Policy\n                                              │\n                                        Dominio propio\n                                              │ misma transacción\n                                     ┌────────▼────────┐\n                                     │ integration_outbox│\n                                     └────────┬────────┘\n                                              │ worker por conector\n                                ┌─────────────▼──────────────┐\n                                │ timeout / retry / breaker │\n                                │ métricas / DLQ / replay    │\n                                └────────────────────────────┘\n\nCheckout/Portal Stripe ─► BillingService ─► Stripe API (Test Mode primero)\n                                 │\n                                 ▼\n                  SaaS customer / subscription / entitlement\n```\n\nEl Connector Hub no es un proxy HTTP arbitrario. Es el borde anti-corrupción (ACL) que traduce contratos externos a eventos/comandos internos versionados.\n\n### Principios\n\n- **Hexagonal / Ports & Adapters:** los servicios de dominio dependen de `ConnectorAdapter`, no de SDKs de Procore/Stripe.\n- **Adapter + Translator:** cada proveedor tiene DTO y errores propios; normalizar solamente los conceptos necesarios.\n- **Inbox + Idempotent Receiver:** recepción durable y una única aplicación lógica por ID de evento.\n- **Transactional Outbox:** el evento saliente se inserta en la misma transacción que el cambio del dominio; el worker lo envía después del commit.\n- **Retry + Circuit Breaker + Bulkhead:** límites por proveedor y por conexión, no globales.\n- **State/Policy versioned:** las decisiones de negocio se apoyan en reglas versionadas; no desplegar BPMN/formularios dinámicos para toda variante antes de necesitarlos.\n- **Least privilege + RLS:** roles separados para HTTP, migrador, worker de proyección y worker de conectores, con permisos explícitos.\n\n## 4. Connector Hub — contratos de aplicación\n\n### 4.1 Interface interna\n\nContrato conceptual; los nombres finales se ajustarán al estilo de paquetes existente:\n\n```java\npublic interface ConnectorAdapter {\n    ConnectorKey key();\n    ConnectorCapabilities capabilities();\n    NormalizedEvent normalizeInbound(VerifiedInboundEvent event);\n    DeliveryResult deliver(OutboundCommand command, ConnectorConnection connection);\n}\n```\n\nReglas del contrato:\n\n- `key()` es un identificador registrado en código (por ejemplo `PROCORE` o `GENERIC_WEBHOOK`), nunca nombre de clase libre en BD.\n- `normalizeInbound` solo recibe un evento que ya pasó la verificación específica del proveedor. No debe asumir que JSON válido equivale a autenticidad.\n- `deliver` recibe una conexión ya autorizada y devuelve un resultado tipado: `DELIVERED`, `RETRYABLE_FAILURE`, `PERMANENT_FAILURE`, `AUTH_REQUIRED`, `RATE_LIMITED`.\n- No permitir que un tenant configure código, expresión SpEL, nombre de clase Java o URL de destino libre para disparar lógica arbitraria.\n- Las capacidades (RFI export, project lookup, webhook inbound, OAuth refresh) se declaran explícitamente y se validan antes de aceptar comandos.\n\n### 4.2 Modelo de conexión\n\nCrear, vía migración aditiva, `connector_connection` con mínimo:\n\n- `tenant_id`, `connection_id`, `provider_key`, `status`, `environment` (`SANDBOX`/`PRODUCTION`), `provider_account_id` opcional, `scopes`, `config_version`, `created_by`, `created_at`, `updated_at`, `last_success_at`, `last_error_code`.\n- `secret_ref` o referencias separadas para access/refresh/client secrets; **no** almacenar tokens o contraseñas en texto plano dentro de JSONB.\n- `public_endpoint_token_hash` (hash de un token aleatorio de alta entropía) para resolver una conexión inbound sin recibir `X-Tenant-Id` del emisor.\n- unicidad por tenant/proveedor/cuenta externa según el modelo de negocio acordado.\n- RLS con `USING` y `WITH CHECK`; pruebas de aislamiento entre tenants.\n\nLa conexión no almacena una URL arbitraria para `base-url` en la primera versión. Cada adapter usa hosts oficiales allowlisted. Un futuro webhook genérico necesita política de egress independiente, DNS/IP revalidation y bloqueo de loopback, redes privadas, link-local y endpoints de metadatos para evitar SSRF y DNS rebinding.\n\n### 4.3 Inbox inbound\n\nAñadir `connector_webhook_inbox`:\n\n- Identidad: `tenant_id`, `connection_id`, `provider_key`, `provider_event_id`, `event_type`, `provider_created_at`, `received_at`.\n- Integridad: `body_sha256`, `signature_verified`, `schema_version`; no registrar cabeceras de autenticación ni tokens.\n- Estado: `RECEIVED`, `PROCESSING`, `PROCESSED`, `RETRY`, `DEAD`; `attempts`, `next_attempt_at`, `lease_until`, `last_error_code`, `processed_at`.\n- Unicidad idempotente sobre la identidad del proveedor, usualmente `(connection_id, provider_event_id)`. No usar un hash del cuerpo como identidad de evento: dos eventos legítimos pueden tener payloads idénticos.\n- Payload mínimo y de retención limitada; si la fuente permite recuperar el recurso autoritativo por API, preferir guardar identificadores y volver a consultar al proveedor.\n- Política explícita de retención/borrado compatible con auditoría y datos personales; no asumir que guardar cada cuerpo íntegro indefinidamente es necesario.\n\n### 4.4 Flujo inbound seguro\n\n1. Limitar tamaño (`Content-Length` y cuerpo leído), content-type, timeout, nesting/JSON y tasa antes de procesar.\n2. Resolver endpoint público aleatorio a la conexión, sin confiar en `X-Tenant-Id`, IDs de tenant incluidos en payload ni query params controlados por el remitente.\n3. Verificar autenticidad usando el mecanismo soportado por el proveedor. La verificación se ejecuta sobre los bytes originales del cuerpo antes de deserializar.\n4. Validar timestamp/replay cuando el protocolo lo soporte; aplicar tolerancia documentada y rotación de secretos.\n5. Validar cuenta/instalación/proyecto externo contra la conexión, tenant y `external_id_map` autorizado.\n6. En una transacción corta insertar en inbox. Evento duplicado ya aceptado: responder `2xx` sin volver a procesarlo. Evento inválido: rechazar sin crear trabajo de dominio.\n7. Encolar/activar worker y responder `2xx` rápido sólo después de confirmar almacenamiento durable.\n8. Worker reclama con `FOR UPDATE SKIP LOCKED` o lease recuperable; normaliza a evento interno, verifica estado/versión y aplica idempotentemente.\n9. Si el proveedor es solo de notificación, consultar el recurso en su REST API para confirmar el estado canónico; completar con reconciliación periódica para eventos perdidos/desordenados.\n10. Fallo transitorio: backoff exponencial con jitter y límite. Fallo permanente o límite agotado: DLQ, alerta y replay manual auditado.\n\n**Procore específico:** la documentación oficial actual describe OAuth 2.0 para la REST API y recomienda emparejar webhooks con reconciliación API, porque los webhooks son señales de mejor esfuerzo y no la fuente canónica del objeto. No asumir que Procore ofrece el mismo encabezado HMAC que Stripe. Verificar el mecanismo exacto que soporte el producto/evento configurado; si no hay firma verificable, usar una URL opaca de alta entropía más comprobación mediante API autenticada, cuotas estrictas y reconciliación, documentando el riesgo residual. Referencias: https://developers.procore.com/documentation/content/introduction, https://developers.procore.com/documentation/content/building-data-connection-apps, https://developers.procore.com/documentation/content/payload-formats\n\n**Stripe específico:** utilizar el SDK oficial para verificar `Stripe-Signature` sobre el cuerpo raw y el secreto endpoint. No implementar HMAC a mano ni compartir el webhook secret con otro proveedor. Referencia: https://docs.stripe.com/webhooks/signature\n\n### 4.5 Outbound real\n\n`integration_outbox` existe, pero la inspección actual no encontró un worker dedicado que la consuma. Resolverlo en vez de crear un segundo outbox innecesario.\n\n- Cambios de dominio y filas de outbox en una única transacción PostgreSQL.\n- El worker reclama lote con lease y `SKIP LOCKED`; ningún HTTP externo dentro de la transacción que cambia el dominio.\n- Guardar `message_id`, clave idempotente estable, número de intento, instante del siguiente intento, error categorizado, proveedor/conexión y timestamps. Añadir una clave única donde el contrato de negocio la determine.\n- Enviar fuera de transacción; registrar el resultado en una transacción nueva y comprobar `status/lease` para no finalizar un trabajo reclamado por otro worker.\n- Retry sólo para fallos transitorios y operaciones idempotentes. `429` respeta `Retry-After`; errores de autenticación requieren reconexión; `4xx` permanentes no se reintentan indiscriminadamente.\n- Circuit breaker y bulkhead por proveedor/conexión. Timeout de conexión y respuesta siempre definidos. Límites de concurrencia y cuota por tenant.\n- Si hay respuesta exitosa remota pero falla el commit local, la operación remota puede repetirse; usar idempotency key del proveedor cuando exista y reconciliación por ID externo. Outbox no significa “exactly-once” en redes: garantiza entrega al menos una vez y requiere consumidor idempotente.\n- DLQ con replay explícito, motivo, actor y audit event; no repetir permanentemente cargas con credenciales inválidas.\n\n### 4.6 Procore adapter\n\nFase inicial sólo RFI push/pull en sandbox. Mantener `ProcoreBridgeService` como fachada de dominio mientras se extrae la llamada síncrona a `ProcoreClient` y se sustituye por la outbox.\n\n- OAuth 2.0 Authorization Code para usuario conectado; añadir DMSA/client credentials sólo cuando el modelo de permisos de Procore lo permita y después de configurar el alcance exacto. Gestionar expiración/revocación/rotación y cifrar refresh tokens con KMS/secret manager.\n- No usar bearer token fijo de ambiente como modelo de producción definitivo.\n- Resolver company/project IDs mediante la cuenta y permisos conectados; no aceptar que el cliente elija arbitrariamente el proyecto remoto.\n- DTOs Procore en el adapter, modelos propios en el dominio, traducción de errores y paginación/rate limits del proveedor.\n- Pruebas contractuales con fixtures sanitizados y sandbox; ningún test automatizado debe tocar producción.\n- El endpoint webhook permanece cerrado hasta autenticar/validar los eventos con el mecanismo real documentado para cada configuración.\n\n## 5. SaaS Billing — contexto distinto del dinero de obra\n\n### 5.1 Borde del dominio\n\nNo reutilizar las tablas `invoice`, `payment` o `payment_application`. El módulo comercial usará nombres prefijados `saas_*` (por ejemplo `saas_customer`, `saas_subscription`, `saas_entitlement`, `saas_webhook_inbox`). Así se evita mezclar el dinero que se paga a subcontratistas con la mensualidad que paga una constructora por usar el SaaS.\n\n**MVP:** setup fee único + suscripción mensual fija. No implementar usage-based billing, Stripe Connect, desembolsos, manejo directo de PAN/CVV ni ledger completo en la primera entrega. El uso medido puede agregarse cuando exista una política comercial real.\n\n### 5.2 Fuente de verdad y límites\n\n- Stripe es autoridad del cobro y los objetos de facturación del proveedor; nuestra BD es la proyección local para acceso, panel y trazabilidad.\n- La autorización de funciones no se concede por el redirect de Checkout ni por un parámetro de la URL de retorno. Sólo cambia al procesar un webhook verificado y aplicar la transición permitida.\n- Ninguna solicitud HTTP pública puede establecer directamente `subscription.status=ACTIVE` ni modificar los IDs Stripe.\n- Catálogo de precios allowlisted: el cliente envía un `plan_code`, nunca un `price_id`, monto, moneda, descuento o tenant de destino libre.\n- Usar Checkout alojado y Customer Portal para reducir la superficie PCI; el backend nunca recibe ni almacena datos completos de tarjeta.\n- El setup fee se representa como línea de cobro separada, con su propio ID de operación e idempotency key; no confundir pago único y recurring price.\n- La factura legal/fiscal mexicana (CFDI) es un flujo separado. Un receipt/invoice de Stripe no debe presentarse automáticamente como CFDI. Requiere decisión fiscal y, si aplica, integración certificada correspondiente.\n\n### 5.3 Tablas propuestas (migración aditiva, después del Connector Hub)\n\n`saas_customer`\n\n- `(tenant_id, saas_customer_id)` PK.\n- `provider` (`STRIPE` para el MVP), `provider_customer_id`, status, timestamps.\n- unique `(provider, provider_customer_id)`; no guardar tarjetas ni client secret.\n- RLS por tenant.\n\n`saas_subscription`\n\n- `tenant_id`, `subscription_id`, `saas_customer_id`, `plan_code`, `provider_subscription_id`, `provider_price_id`, `status`, `currency`, `current_period_start`, `current_period_end`, `cancel_at_period_end`, `grace_until`, `version`, timestamps.\n- estados enumerados/validados explícitamente (`PENDING_CHECKOUT`, `TRIALING`, `ACTIVE`, `PAST_DUE`, `PAUSED`, `CANCELED`, `INCOMPLETE`, `UNPAID`). No mapear cualquier string del proveedor sin validación.\n- unique IDs de proveedor y claves compuestas que impidan asociar una suscripción a otro tenant.\n- RLS + `WITH CHECK`; las actualizaciones vienen del servicio autorizado de webhooks y comandos admin explícitos.\n\n`saas_entitlement`\n\n- `tenant_id`, `feature_key`, `source_subscription_id`, `enabled`, `valid_from`, `valid_until`, `policy_version`, `updated_at`.\n- Proyección derivada de plan + estado de suscripción + política de gracia. No permitir modificarla desde el frontend.\n- Los guards de API comprueban entitlement server-side, además de RBAC y tenant.\n\n`saas_provider_event`\n\n- `provider`, `provider_event_id`, `received_at`, `signature_verified`, `payload_sha256`, `event_type`, `processing_status`, `attempts`, `processed_at`, `last_error_code`.\n- unique `(provider, provider_event_id)` para idempotencia global de la cuenta/plataforma; tenant se vincula después de mapear el customer/subscription a IDs internos.\n- RLS no se aplica ingenuamente a una cola central sin tenant conocido: la ingestión inicial requiere rol dedicado y permisos mínimos; el worker obtiene tenant desde el mapa verificado de customer/subscription. Ninguna clave del payload define el tenant por sí sola.\n\n`saas_usage_event` (opcional fase 2, no requisito del MVP)\n\n- append-only, `tenant_id`, `event_id`, `feature_key`, `units`, `occurred_at`, `source`, `idempotency_key`, `pricing_version`.\n- unique para la clave de idempotencia; agregados como proyección reconstruible. Definir explícitamente qué acciones son facturables y cómo se corrigen eventos.\n\n### 5.4 Estados y eventos de suscripción\n\n- `checkout.session.completed`: registrar correlación y confirmar el customer/subscription referido; no basta por sí solo para activar si la modalidad requiere primer pago confirmado.\n- `invoice.paid`: confirma pago de la factura del proveedor; actualizar estado con reglas idempotentes.\n- `invoice.payment_failed`: mover a `PAST_DUE` o a estado definido por política, aplicar período de gracia configurable y notificar.\n- `customer.subscription.updated` / `.deleted`: reconciliar status, periodos y cancelación.\n- `entitlements.active_entitlement_summary.updated`: considerar sólo si se decide que Stripe Entitlements sea autoridad para los features; no duplicar dos modelos de verdad sin ADR.\n\nLos webhooks pueden llegar duplicados o desordenados. Deduplicar por ID de evento; validar la transición; si el evento está obsoleto o existe ambigüedad, consultar el objeto canónico en Stripe antes de modificar la proyección. Añadir job de reconciliación para detectar suscripciones locales divergentes.\n\n### 5.5 Idempotencia y operación\n\n- Idempotency key estable por operación semántica (`tenant + operation + internal command id`) al crear customer/checkout/subscription. No utilizar correo ni dato personal como clave.\n- Registrar respuesta externa mínima y provider IDs; no almacenar headers sensibles ni loguear secretos.\n- Cada webhook válido se guarda durable antes de responder 2xx. Reprocesarlo nunca duplica entitlements ni onboarding.\n- No ejecutar efectos externos dentro de la transacción local. Para provisioning/checkout usar un estado persistente más outbox/worker; compensaciones explícitas para recursos remotos creados parcialmente.\n- Revisión de monedas e impuestos: el precio y moneda provienen del catálogo publicado; si el negocio vende en MXN y/o EUR debe decidir impuestos, factura fiscal, zona geográfica y condiciones contractuales antes de producción.\n\nReferencias oficiales: https://docs.stripe.com/webhooks/signature, https://docs.stripe.com/api/idempotent_requests, https://docs.stripe.com/api/events/types\n\n## 6. API propuesta (MVP cerrado por permisos)\n\n### Connector Hub\n\n- `GET /api/connectors` — lista conexiones visibles al tenant actual, sin secretos.\n- `POST /api/connectors/procore/authorize` — inicia OAuth con `state` aleatorio, PKCE cuando aplique, redirect URI allowlisted y nonce de corta duración.\n- `GET /api/connectors/procore/callback` — valida state, intercambia código server-side y persiste sólo secreto cifrado/referencia de vault.\n- `POST /api/connectors/{connectionId}/test` — prueba de conectividad/autorización con cuotas.\n- `POST /api/connectors/{connectionId}/sync` — encola una reconciliación, no bloquea el request.\n- `GET /api/connectors/{connectionId}/deliveries` — auditoría paginada, valores sanitizados.\n- `POST /api/connectors/{connectionId}/deliveries/{messageId}/replay` — sólo rol de operación autorizado, idempotencia y audit event.\n- `POST /api/connectors/webhooks/{opaqueEndpointToken}` — endpoint público por proveedor; no exige `X-Tenant-Id` del remitente. El endpoint opaco sólo selecciona configuración y NO sustituye la autenticación criptográfica cuando el proveedor la soporta.\n\nNo exponer un endpoint genérico para configurar cualquier host HTTP en MVP.\n\n### SaaS Billing\n\n- `POST /api/saas-billing/checkout` — requiere user auth + permisos de owner/admin; acepta `plan_code` y `request_id` idempotente, no importe ni price ID.\n- `POST /api/saas-billing/portal` — genera URL de portal para el customer interno correlacionado.\n- `GET /api/saas-billing/subscription` — lectura del estado local y periodo, sin consultar Stripe en cada request.\n- `POST /api/saas-billing/webhooks/stripe` — raw body, verificación de firma mediante SDK oficial, almacenamiento durable de evento y deduplicación.\n- `GET /api/saas-billing/invoices` — lista proyecciones de facturación del proveedor y enlaces de hosted invoice sólo si proceden del provider.\n\nNo añadir endpoints para cambiar directamente plan, estado o entitlement sin una operación de negocio controlada.\n\n## 7. Estados de operación y recuperación\n\n### Outbound delivery\n\n```text\nPENDING -> PROCESSING -> SUCCEEDED\n                    \-> RETRY -> PROCESSING\n                    \-> DEAD (terminal; replay manual auditado)\n```\n\nLeases vencidos recuperables; un worker reiniciado no deja fila permanentemente en `PROCESSING`. Un timeout remoto no implica que el proveedor no procesó el comando: resolverlo por clave idempotente/lectura autoritativa antes de reenviar.\n\n### Subscription\n\n```text\nPENDING_CHECKOUT -> TRIALING / ACTIVE\nACTIVE -> PAST_DUE -> ACTIVE\nACTIVE -> CANCELED (inmediato o al fin del periodo)\nPAST_DUE -> UNPAID / CANCELED según política contractual\n```\n\nCambiar entitlements según una tabla de decisión versionada: no borrar datos si vence la suscripción; restringir nuevas escrituras o workflows nuevos con periodo de gracia acordado; mantener export de datos y soporte administrativo según contrato.\n\n## 8. Seguridad, abuso y privacidad\n\n| Amenaza | Control obligatorio |\n|---|---|\n| Webhook falsificado/replay | Firma del proveedor sobre raw body, timestamp, deduplicación, rotación de secreto; mecanismo específico por proveedor |\n| Tenant spoofing | Tenant proviene del credential/connection mapping verificado, no de header/body externo |\n| SSRF de webhook genérico | No habilitar destino libre; allowlist, egress control, validación DNS/IP, bloquear redes privadas/link-local/metadata y redirects |\n| Token OAuth filtrado | Vault/KMS, cifrado, scopes mínimos, rotación/revocación, redacción en logs |\n| Payload malicioso | Límite de tamaño, schema validation, content-type, parser seguro, no deserialización polimórfica, no ejecución de scripts |\n| Doble procesamiento | Uniqueness constraints, inbox/outbox, handlers idempotentes, prueba de carreras |\n| Provider caído | Timeout, rate limit, circuit breaker, bulkhead, backoff+jitter y DLQ |\n| Envío de eventos a cliente equivocado | Validación cuenta externa ↔ conexión ↔ tenant ↔ mapping; no confiar en ID incluido en payload |\n| Cobro SaaS duplicado | Idempotency keys servidor a proveedor, IDs únicos, webhook dedup, reconciliación |\n| Escalada de plan/entitlement | Checkout creado por backend desde catálogo; eventos verificados como fuente de estado; guards server-side |\n| Exposición PCI/PII | Hosted Checkout/Portal; no PAN/CVV; payloads minimizados, retención, redacción y logs sin secretos |\n| Abuso de replay/sync | RBAC de operación, auditoría, rate-limit por tenant y conexión, cuotas y aprobación para acciones de producción |\n\nLos permisos de GitHub Actions también deben ser mínimos y las actions externas fijarse a SHA completo. No otorgar `contents: write` a jobs de compilación o análisis; reservar escritura para jobs separados y acotados. Referencia: https://docs.github.com/en/actions/reference/security/secure-use\n\n## 9. Observabilidad y soporte\n\nMétricas sin etiquetas de alta cardinalidad ni PII:\n\n- `connector_webhook_received_total{provider,result}`\n- `connector_webhook_duplicate_total{provider}`\n- `connector_delivery_total{provider,result}`\n- `connector_delivery_attempts`, `connector_delivery_latency_seconds`\n- `connector_dead_letter_total{provider}`\n- `saas_billing_webhook_total{type,result}`\n- `saas_subscription_state_change_total{from,to}`\n\nCada solicitud interna lleva `trace_id`, `tenant_id` sólo en el contexto de observabilidad protegido y correlation/idempotency IDs; nunca tokens, API keys, payloads completos o información sensible en logs. Dashboard con última sincronización, latencia, autenticación vencida, retries, DLQ y discrepancias de reconciliación.\n\n## 10. Pruebas de aceptación obligatorias\n\n### Connector Hub\n\n1. Firma inválida no crea inbox ni mutación de dominio.\n2. Firma válida se persiste y responde rápido; si la persistencia falla, no se responde 2xx.\n3. Repetir un mismo `provider_event_id` N veces genera una única aplicación lógica.\n4. Eventos fuera de orden no revierten estado nuevo ni saltan una transición permitida.\n5. La misma conexión no puede mapear recursos de otro tenant.\n6. El payload externo no puede seleccionar `tenant_id`, handler Java o destino arbitrario.\n7. Errores 429/5xx reciben reintento apropiado; errores 400/401 persistentes no generan tormenta de retries.\n8. El worker puede morir después de reclamar, expirar lease y recuperar la fila.\n9. Un timeout tras éxito remoto no provoca duplicado funcional.\n10. Circuit breaker abierto protege a las otras conexiones/proveedores.\n11. Webhook perdido se recupera mediante reconciliación.\n12. Logs/metrics no exponen tokens, firmas o datos personales.\n\n### SaaS Billing\n\n1. Sólo catálogo servidor decide el `price_id`, importe y moneda.\n2. Cliente A no puede consultar customer/subscription/portal del tenant B.\n3. Checkout duplicado por request id retorna la misma operación o resultado estable.\n4. Signature inválida no cambia subscription ni entitlement.\n5. Evento Stripe duplicado no duplica estado/entitlements.\n6. Eventos desordenados no regresan una suscripción a un estado obsoleto.\n7. `invoice.payment_failed` aplica grace policy; el frontend no se concede estado `ACTIVE` por redirect.\n8. `invoice.paid` sólo afecta la suscripción vinculada a customer y tenant previamente correlacionados.\n9. Renovación, cancelación al fin del periodo, cancelación inmediata, reembolso/disputa y estado `unpaid` tienen transiciones definidas.\n10. Reconciliación detecta divergencia entre provider y DB sin doble cobro.\n11. El test usa Stripe Test Mode/fixtures; no credenciales ni cobros reales.\n12. RLS y permisos de DB se prueban contra PostgreSQL real con rol runtime, no sólo admin.\n\n### Gate para merge/release\n\n- `mvn -B -ntp clean verify` verde en JDK 21.\n- Migraciones V1–V22+ contra base vacía y estrategia documentada para instalaciones heredadas.\n- Testcontainers PostgreSQL para RLS, constraints, idempotencia/concurrencia y leases.\n- Pruebas de contrato del adapter con fixtures y sandbox si está disponible.\n- CodeQL, dependency review, secret scanning y Compose validation.\n- Revisar SBOM/árbol real de dependencias y licencias.\n- Evidencia de backup/restore y rollback para migraciones de estado.\n- Revisión manual del diff final y aprobación humana explícita antes de producción.\n\n## 11. Revisión crítica del generador “Parte 6” aportado\n\nNo integrarlo literalmente. Riesgos y defectos observables:\n\n1. **Colisión Flyway:** intenta crear V15, pero V15 ya existe; sería una migración con versión duplicada.\n2. **Identidad de tenant:** el `TenantContext` actual procede del header. Para una plataforma multi-tenant, la selección de tenant debe ligarse a la credencial autenticada; no basta que el request mande un UUID.\n3. **SQL y RLS:** no concatenar contextos/valores al SQL. Usar `set_config('app.tenant_id', ?, true)` en la misma transacción/connection; verificar rol real y RLS.\n4. **JSONB:** asumir que `jdbc.queryForMap` devuelve `String` para `jsonb` puede fallar según driver (puede ser `PGobject`). Deserializar a DTO de manera explícita.\n5. **Validación de esquema insuficiente:** sólo revisa presencia de campos; no valida tipos, campos extra, tamaños, patrones, enum de opciones, nulabilidad ni versión del schema. El `required` no está expresado formalmente.\n6. **Process key controlado por datos:** cargar `process_key` de BD y llamar `startProcessInstanceByKey` sin allowlist/versionado permite iniciar cualquier proceso desplegado con variables no apropiadas. Exigir registro aprobado de modelo, versionado y permisos.\n7. **Sin idempotencia ni auditoría:** cada retry genera UUID/instancia BPMN nueva; no hay request key ni registro de quién inicia el trabajo.\n8. **Form renderer incompleto:** `any`, `parseFloat`, opciones controladas desde datos y ausencia de manejo de error/estado accesible. No integra automáticamente `embedded:app:forms/dynamic.html` con una app React externa.\n9. **Módulos incompatibles con código existente:** importa `com.tuempresa.platform.tenant.TenantContext`, pero se debe revisar el contrato real; usa `RuntimeService` de paquete Camunda aunque el objetivo debe fijar la versión/motor y evitar mezclar Operaton con Camunda sin decisión explícita.\n10. **SLA sin timer durable:** guardar `sla_hours` no instala un timer BPMN ni define calendario/feriados/escalamiento.\n11. **Plantillas globales sin lifecycle:** no hay estados DRAFT/APPROVED/RETIRED, vigencia, versión de esquema, actor aprobador o auditoría de cambio.\n12. **Falta autorización funcional:** no verifica membership/rol sobre la clase de tarea, cuota por tenant, ni si el actor puede iniciar ese `taskType`.\n\nPrimero cerrar Connector Hub y los boundaries de identidad; diseñar Template Registry como una iteración separada con migración V24+ y contrato de formularios validado, no colarlo dentro de V22/V23.\n\n## 13. Dependencias nuevas: política\n\nNo añadir un paquete sólo por moda.
