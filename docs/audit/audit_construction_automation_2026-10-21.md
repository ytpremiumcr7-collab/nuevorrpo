Cambios principales\n\n### Autenticación, tenant y autorización\n\n- `X-User-Id` queda deshabilitado por defecto; el modo de desarrollo debe activarse explícitamente.\n- La búsqueda de API key se hace mediante hash y dentro del tenant suministrado.\n- El bootstrap requiere un secreto, tiene comparación de tiempo constante, bloqueo por fila del tenant y emite una API key que se almacena como hash.\n- Se añadió una autorización por proyecto y se quitaron varias decisiones de actor confiadas a campos del cuerpo HTTP.\n- Las consultas del dashboard y de colas operativas se limitan por membresías de obra y tienen límites de paginación.\n- El contexto RLS se configura dentro de transacciones de base de datos donde corresponde; los filtros limpian su contexto de thread al concluir la petición.\n\n### Pagos y controles de workflow\n\n- La factura, el proyecto, el contrato, el subcontratista, el monto y la versión de compliance se vuelven a comprobar contra datos persistidos.\n- La evaluación three-way rechaza órdenes de compra de otra obra, líneas duplicadas y conjuntos de líneas asimétricos.\n- Las compuertas BPMN de cumplimiento y three-way match son *fail-closed*.\n- El delegate deja una instrucción `PENDING`; no afirma que haya aprobación final ni que una transferencia bancaria se haya ejecutado.\n- La migración añade una unicidad para evitar pagos duplicados por una misma solicitud. Debe medirse si existen duplicados históricos antes de aplicar V17 a una base con datos.\n\n### Outbox e integraciones\n\n- El claim transversal del outbox ya no está concedido al rol de API `app_user`; se reserva al rol `outbox_worker`, configurado por una conexión/pool separado.\n- Los eventos sin handler provocan error/reintento y no se marcan silenciosamente como procesados.\n- Los scripts de inicialización configuran las credenciales de `app_user` y `outbox_worker` después de crear sus roles.\n- El gate de RLS ahora inspecciona tablas operativas que tengan `tenant_id`, evitando clasificar tablas globales de Camunda como tablas tenant de la aplicación.\n- Se corrigió la discrepancia de Compose entre la contraseña que inicializa el rol `postgres` y la contraseña suministrada a Flyway.\n- Procore inbound y el envío de ofertas devuelven `501 NOT_IMPLEMENTED` hasta implementar la verificación de firma/identidad, el enrutamiento tenant-proyecto y la atribución confiable al contratista. Es un cierre explícito, no una funcionalidad terminada.\n\n## 3. Bloqueadores de release\n\n### P0 — Migraciones con credencial superuser en el proceso HTTP\n\nLa aplicación aún usa Flyway al arrancar con `SPRING_FLYWAY_USER=postgres`; por eso el contenedor HTTP recibe la contraseña superuser. La candidata alinea esa contraseña con la que realmente inicializa PostgreSQL, pero **no elimina el riesgo de privilegios**. Antes de producción debe moverse la migración a un job/runner aislado y quitarse la credencial superuser del contenedor HTTP.\n\n### P0 — Aprobación de pago y liquidación bancaria\n\nEl DMN `nivelAprobacionPago.dmn` no está conectado al BPMN de pago. No se ha demostrado un registro durable de aprobación humana/política ni una integración de banco, callback, idempotency key del proveedor o conciliación. Mantener el estado pendiente y no habilitar transferencias reales.\n\n### P1 — Autorización completa\n\nLos controles incorporados afectan los endpoints y servicios identificados, pero no se demostró una matriz negativa completa para todos los controladores, servicios, jobs y delegates BPMN. Se necesitan pruebas cross-tenant y cross-project con roles reales de base de datos.\n\n### P1 — Migración y outbox\n\n- Aplicar V17 sobre base vacía y sobre una copia de datos; comprobar duplicados antes de crear `ux_payment_one_per_application`.\n- Verificar que `outbox_worker` tiene LOGIN y no posee `SUPERUSER`, `BYPASSRLS`, `CREATEROLE` ni `CREATEDB`; confirmar que `app_user` no ejecuta la función de claim.\n- Probar concurrencia, caída del worker, reintentos, dead-letter y recuperación con PostgreSQL real. La prueba actual usa inspección estática y el entorno local no replica los permisos del worker.\n\n### P1 — Gaps de producto/integración\n\n- Completar el contrato de identidad `app_user` → `party` antes de habilitar el envío de ofertas.\n- Implementar y verificar autenticidad y procesamiento de webhooks entrantes Procore antes de reactivarlos.\n- La generación de formularios OSHA debe permanecer bloqueada hasta completar mapeo, revisión normativa y pruebas.\n- Probar seguridad de Actuator, secretos, backups/restauración y configuración efectiva de producción.\n\n## 5. Decisión recomendada\n\nAceptar el paquete solo como **candidata de hardening para la siguiente iteración**. No etiquetar, publicar ni desplegar como release de producción hasta cerrar ambos bloqueadores P0 y demostrar `mvn clean verify`, despliegue real de PostgreSQL/Flyway, RLS con roles no propietarios, autorización cross-tenant/project y ejecución de BPMN/DMN en Camunda.\n\n## 6.
